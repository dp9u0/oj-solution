# 题解写作规范(Solution Spec)

PG Writing-DNA 在本仓库的应用规范,管辖 3530 个已解题的题解补齐工作。
上游为 `writing-dna/pg/` 下的 Writing-DNA 及语言/结构/认知分层产物;尚未同步时本文件的第 2 节声
音契约生效,同步落地后以 DNA 为准,冲突处改 DNA。

## 0. 决策记录(用户已拍板)

| 项 | 决定 |
|---|---|
| 范围 | 全量 3530 题逐题过检,不预先缩范围;分级处理 |
| 核心 | 题解的核心是解题思路(the insight);不写击败百分比,不 re-submit 拿数据 |
| 存放 | 集中式 `essays/`;**现有 README/Solution 一律不动**,冻结为"题目描述+代码"的记录 |
| 语言 | 正文英文;篇末规则句中英双语 |
| git | 可 commit,粒度见第 7 节 |

注:分级 P(补思路段)的产出物同样放 `essays/`,不回填 README——理由同上,"补"指补一篇短文,
不是改旧文件。这是本规范替审阅人做的一个默认,不同意就改第 0 节。

## 1. 分级判定

三级:**E**(全篇 essay)/ **P**(思路段)/ **S**(跳过,只留 triage 记录)。

判定程序——读该题 README 思路段 + `solution.js` 后,依序回答,首个命中即定级:

```
Q1  显然解是否就是正解?
    「显然解」= 从题面直接翻译的做法:暴力枚举、按题意逐步模拟。
    约束放行(小 n、无最坏数据压力),或正解只是把显然解照写一遍 → S。

Q2  从显然解到正解,是否只是套用一件有名字的标准工具?
    标准工具 = 换数据结构(数组→哈希表/堆/队列)、加记忆化、前缀和预处理、
    排序+双指针、模板化 DFS/BFS——不改变思考对象的那一步。
    是,且没有别的弯 → P。

Q3  正解是否要求重构问题,或显然解的补法存在非平凡的坑?
    「重构」= 改变迭代的对象/方向/搜索空间:
      · 索引 → 边界/状态/值域(答案二分:不在数组上搜,在值域上搜)
      · 正序 → 逆序、从终点反推
      · 「对每个 i 求…」 → 「维护自 i 起的性质」
      · 逐个计数 → 差分/按余数分组/按位分组
      · 把序列看成图、把选择看成状态压缩
    是 → E。
```

**升级信号**(Q2 命中后检查,任一命中改判 E):
- `solution.js` 的实际做法与 README 既有笔记结构不一致——当年走过路线变化,故事真实存在
- 存在两个可行解法族,取舍取决于非显然的约束分析(如 3Sum:哈希 vs 排序+双指针)
- 约束算术上显然解死于一个反直觉的具体原因(不是单纯"太慢",而是"快了也错")
- Remark 列有 `:+1:`
- 重解题时产生真实的"这样也行?"惊讶,重推一遍后确认成立

**降级信号**(Q3 命中后检查,任一命中降 P 或 S):
- 重构只有一步,且该步骤本身是教科书内容(如"反向 DP")
- 全部洞察可压缩进一句话而无损失
- 洞察只是语言机制(BigInt、自定义 comparator、位运算符)

**边界规则**:拿不准时向"仍装得下洞察的最便宜产出物"靠——洞察在但弧线不清 → P;P 要超过
120 词才能说清 → E;一句话说完 → S。复核与写作阶段均可升降级,必须同步改 triage.tsv 的
signal 说明理由。

**诚实性条款**:E 的"误解"必须能从题面+约束推导——显然解及其失败是任何解题者都会撞上的
标准路径,不是编造的个人经历。存量题没有弯路记忆,第 1 拍素材一律用"显然解怎么死"来立;
连这也立不住的题,不配 E,降级。

## 2. 声音契约(DNA 同步前的替代品)

- 短陈述句;第一人称;具体名词和数字优先于抽象名词。
- 直接给结论,不写"本文将介绍/让我们来看"。
- 不确定就说不确定,不装完整。
- 禁:corporate 语气、空泛总结段、emoji、step-by-step 流水账、代码逐行解说。
- 技术事实(复杂度、边界、失败原因)必须精确;声音是外壳,论证是骨头。

## 3. 产出物模板

文件命名:`essays/NNNN-slug.md`(slug 取英文标题 kebab-case;lcci/lcp/lcr/lcs 用
`essays/<id>-slug.md`,如 `lcci-01.01`;英文标题取不到则只用 id)。

两类产出物共用同一文件骨架:

```markdown
# NNNN. <EN Title>
<leetcode.cn 链接,取得到就放> · <L> · <tags>

<正文>

---

**Rule:** <EN 一句话>
**规则:** <中文一句话>
```

题意不设独立段,以不超过一句话织入正文第 1–2 拍;读者读完首段应能不必翻题面。

### 3a. E:全篇 essay(五拍)

| 拍 | 任务 | 字数 |
|---|---|---|
| 1 断言开篇 The claim | 一句可反驳的断言:说出那个误解,或令人意外的真相。不铺垫 | 25–50 |
| 2 翻转 The flip | 用约束算术或反例杀死直觉:显然解为什么注定失败 | 60–120 |
| 3 装置化展开 The device | 命名并搭建那个机制:重构如何发生、维护什么不变量。代码只以证据出现 | 150–300 |
| 4 自我供证 The proof | 复杂度算术对上约束数字、边界情形、对示例走一遍 | 60–150 |
| 5 规则化收尾 The rule | 提炼一条可复用规则,双语(见骨架) | 25–60 |

- 正文合计 320–680 词,硬上限 750。词 = 空白分隔 token,不含 header 与代码块。
- 主代码段 ≤25 行,只放承重部分(装置本身),不放完整提交代码;可选对比段 ≤10 行。
- 复杂度必须出现在第 4 拍,写成算术(哪个量乘哪个量、对上 n 的约束值),不写裸结论。
- 互引:允许相对链接到同 tag 批内其他 essay(同波次内必然已存在),如 `[0004](./0004-…md)`。

### 3b. P:思路段(三句式)

1. **断言开场**(≤2 句):说出那个非显然事实。
2. **推理链**(2–4 句):每句一步推断,具体、含复杂度。
3. **双语规则句收尾**(见骨架)。

合计 60–110 词,硬上限 120。字数一到顶就说明它该是 E——回去重判,不要压缩语义来凑格式。

### 3c. S:无产出物

只在 triage.tsv 留一行 signal,不改任何文件。

## 4. 全量检查执行方式

进度唯一事实源:`essays/triage.tsv`,TSV,首行表头,每题一行:

```
problem	title	range	L	tags	tier	signal	output	status
0004	Median of Two Sorted Arrays	0000-0099	Hard	[bs]	E	<≤120字符判定理由>	essays/0004-median-two-sorted.md	written
```

- tier ∈ E/P/S;status ∈ todo/triaged/written/reviewed;S 的 output 为 `-`。

**阶段 0 · manifest**:一次性脚本(执行期落 `scripts/triage-manifest.js`)从 84 个 chunk 表 +
lcci/lcp/lcr/lcs 生成 3530 行机械字段(problem/title/range/L/tags/tier=todo)。

**阶段 1 · 分批判读**:一批 = 一个 chunk 文件(>250 行的批可对半拆)。子代理并发 ≤3,每代理
对自己批内每题执行第 1 节判定程序,产出批 fragment(`essays/triage/<range>.tsv`,含 tier +
signal)。时间盒:S 确认 ≈1 分钟/题,P/E 判定 ≤5 分钟/题;时间盒是节奏指导,不是精度牺牲。

**阶段 2 · 合并抽查**:fragment 排序合并为 canonical triage.tsv。复核协议:**E 全部由我本人
重读复核**(essay 是最贵的产出物,假阳性最贵);P 抽 20%;S 扫 signal 行 + 抽 5% 深查。

**阶段 3 · 写作波次**:
- Wave 1:全部 E,按 tag 聚类排批(同批共享心智模型,可互引),批内按题号升序。
- Wave 2:全部 P,按 chunk 顺序推进。
- 写作中若发现洞察比 triage 记录大/小,就地升降级并回写 triage.tsv。

**阶段 4 · 索引**:chunk 表加 Essay 列,链接该题产出物(E 和 P 都链,S 不链),随该批提交。

## 5. 触发升级为 essay 的信号清单(判读期速查)

1. 约束算术杀死显然解,且死因反直觉("快了也错"优于"只是慢")
2. 正解需要重构(第 1 节 Q3 的任何一种对象变化)
3. 两个解法族的真实取舍
4. 代码与既有笔记路线不一致
5. 重解时的真实惊讶
6. `:+1:` 标记(至少保 P,复查后可升 E)

命中 1/2/3 之一基本就是 E;4/5/6 是复核信号,单独命中时先过降级信号再定。

## 6. 语言与写作细则

- 正文英文;规则句双语(EN 一句 + 中文一句,语义等价,不强求逐词)。
- 术语用行业通用形式(monotonic stack、difference array),不生造中英混合词。
- 数字写实值:n ≤ 10^5 就写 10^5,不写"很大"。
- 每篇自成一体:读者不翻 README 也能读完。

## 7. git 提交粒度

一次 commit = 一个可审单元:

| 提交 | 内容 | 信息 |
|---|---|---|
| 规范+DNA | 本文件及同步的 DNA 产物 | `docs: add PG solution spec and writing DNA` |
| triage 批 | 该批 fragment 合并入 triage.tsv | `triage: <range>` |
| essay | 单篇 essay + triage 行 status + chunk 表链接 | `docs(essays): NNNN <slug>` |
| paragraph 批 | 该 chunk 全部思路段 + 对应 triage/chunk 更新 | `docs(essays): P <range>` |

只 commit 不 push;push 需明确指示。仓库现存 1 个未推送提交与本工作无关,不动。

## 8. 验收

每篇定稿前自检:字数区间、五拍齐、规则句双语、复杂度在第 4 拍成算术、无 step-by-step 流水账、
技术事实与 `solution.js` 一致。验收方为本端按 PG checklist 终审;一篇以一轮修订为限。
